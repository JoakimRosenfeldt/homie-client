01 / Executive readout

The concept is sound. The prototype is not yet a beta.

Homie already has a distinct visual voice, a clear rental context, and the beginnings of a useful two-sided product. The main risk is not visual polish. It is that the interface promises more than the product currently does. Several controls are inert, the renter and landlord journeys compete for the same navigation, and core trust, accessibility, and state handling are missing.

Keep

The current identity

The terracotta and cool blue-gray palette, Figtree typography, rental-specific copy, card language, and restrained warmth feel like Homie. Refine this system instead of replacing it.

Change first

The product contract

Every visible control must work, every role must have a clear home, and every application must lead to a legible state. Until that is true, more surface area will deepen the prototype gap.

02 / Product decisions

Locked decisions

These choices came out of the product grilling and remove the main ambiguities before implementation.

Area Decision Consequence
Audience Room seekers are the primary user. Everyone can also create a native listing. Seeker tasks define the main tabs. Host work lives under You.
Navigation Explore, Applications, Inbox, You. Remove Applicants and Matches as peer tabs. Add a separate host dashboard under You.
Inventory Rooms, studios, apartments, and houses across Denmark. Add studio to the backend listing type and branch relevant fields by rental type.
Language English and Danish UI. Start from device locale and allow an override in You. Use typed local dictionaries and Intl. Keep user-written listing text in its original language.
Identity No account system for beta. Use a device-only secret stored with SecureStore. No recovery or cross-device sync. State this clearly during onboarding and deletion.
Profile gate Browsing is open. A profile is required before the first application. Do not block exploration with onboarding. Trigger the smallest relevant profile flow at intent.
Application Send an immutable profile snapshot plus an optional note. Later profile edits must not change an application already reviewed by a landlord.
Conversation Chat opens only after a landlord shortlists an application. Applications need explicit statuses and server-enforced transitions.
Publishing Valid native listings publish immediately. Trust comes from rate limits, reporting, blocking, and takedown instead of manual pre-approval.
Location Manual city or area first. Ask for device location only after the user chooses Near me. Remove the launch-time permission prompt and avoid needless third-party reverse geocoding.
Map privacy Keep exact coordinates private. Show a deterministic public coordinate displaced by about 250 meters. Public pins remain stable without exposing an exact home address.
Retention Applications and chats remain until the device owner deletes their data. Add an explicit Delete my data flow and server-side cascade behavior.
Metric Submitted applications that become shortlisted conversations. Instrument event timestamps in first-party data. Skip a third-party analytics SDK for beta.
External inventory is out of scope

Do not scrape BoligPortal or Lejebolig. Their published terms restrict unauthorized crawling and reuse. Native inventory is slower to seed, but it avoids legal, reliability, and duplicate-listing debt. See BoligPortal's policy and Lejebolig's terms.

03 / UI review

What works and what blocks release

The live app was reviewed at 390 × 844 and 1280 × 800 across Explore, Applicants, Matches, You, onboarding, search agent, new listing, room detail, and chat. Source structure and current accessibility behavior were also inspected. The app does not read as generic AI output. Its voice is specific. The repeated rounded cards, pills, and striped placeholders are the main prototype tells.

Visual system

Centralized light and dark tokens, consistent spacing, readable mobile hierarchy, and a recognizable color relationship provide a solid base.

Product voice

Copy is concrete to Danish rentals. The interface feels warmer and more purposeful than a generic marketplace template.

Motion restraint

The swipe flow respects reduced motion during commit. That same restraint should guide future micro-interactions.

  1. P0
    01

    Visible controls do not complete actions

    Photo slots, listing inputs, private note, save-search text, sort, profile settings, and the room-card heart either do nothing or suggest a different action. Remove each promise until it works, or connect it to persistent state.

  2. P0
    02

    Renter and landlord jobs share one tab bar

    Explore, Applicants, Matches, and You mix roles and make the product model hard to learn. The settled navigation gives renters a stable home and moves host work into its own dashboard.

  3. P0
    03

    Contrast fails in both themes

    Examples include faint light text at about 2.66:1, muted light text at about 4.02:1, inactive tabs at about 2.14:1, and white text on the dark accent at about 3.3:1. Token changes can fix this systemically.

  4. P0
    04

    Keyboard and screen-reader contracts are incomplete

    Modals lack dialog semantics and focus containment. Selected chips do not expose state. The slider lacks value attributes, focus, and keyboard support. The web build has no visible focus ring.

  5. P0
    05

    Tap targets are too small

    Several controls are below the 44 × 44 point baseline, including Map, filter chips, back controls, New agent, and onboarding close controls. Increase the hit area even when the visible icon stays small.

  6. P1
    06

    Desktop web stretches mobile layouts

    Cards expand to about 1240 pixels and tab items to about 250 pixels. Use a centered content shell and treat web as a demo surface, not as a stretched phone.

  7. P1
    07

    The app asks for location too early

    An automatic permission prompt on launch spends trust before the user asks for a nearby search. Start with manual area selection and make Near me the explicit trigger.

  8. P1
    08

    The map is a visual placeholder

    The current map cannot support search, privacy, or movement behavior. Replace it with a native map that uses approximate public pins and bounded viewport queries.

  9. P1
    09

    System states are absent

    Real loading, empty, error, offline, permission-denied, success, and destructive confirmation states are required before live data replaces mocks.

  10. P2
    10

    Small text and semantics need a full pass

    Some labels sit at 10 to 12 points. There is no consistent heading or landmark model and no clear image alternative-text model. Verify at 200% text size and with VoiceOver and TalkBack.

Implementation evidence from the current code
  • Design tokens are centralized in src/theme/tokens.ts, so contrast repairs can be made at the system level.
  • The custom slider in src/components/slider.tsx needs a native and web-accessible replacement.
  • Filters, listing creation, and match flows contain modal behavior that needs one shared accessibility contract.
  • The client still reads from the in-app store in src/features/nabo/store.tsx. Convex is not yet wired into the browse flow.
  • The Convex schema already contains listings and saved listings, with ownership and private-address redaction behavior covered by tests.

04 / Target experience

One clear seeker journey, with host tools one level down

The core journey should be easy to explain in one sentence: browse freely, create the right profile when you apply, then move into a conversation only after the landlord shortlists you.

  1. ExploreBrowse list or map, filter, sort, and save.
  2. Profile gateComplete a shared-home or private-rental profile.
  3. ApplyReview snapshot, add an optional note, submit once.
  4. ApplicationTrack pending, shortlisted, declined, withdrawn, or closed.
  5. InboxChat becomes available after shortlist.

Shared-home profile

  • Name and photos
  • Short introduction
  • Occupation or study
  • Move-in date and expected stay
  • Budget
  • Household habits

Private-rental profile

  • Household size
  • Employment or study
  • Optional income range marked as unverified
  • Move-in date
  • Optional note
Tab Purpose Primary content
ExploreFind and save homes.Browse and Saved segments, filters, sort, list, map, saved-search alerts.
ApplicationsTrack submitted interest.Status, property summary, submitted snapshot, withdraw action, route to chat after shortlist.
InboxContinue shortlisted conversations.Conversation list, unread state, message thread, report and block.
YouManage identity, preferences, and hosting.Profile, language, notifications, host dashboard, create listing, privacy, delete data.
Host review keeps the swipe deck

Keep the existing interaction as a secondary review mode. Add visible Pass and Shortlist buttons, open the full applicant profile on tap, and provide one-step undo. No essential decision can depend on a gesture alone.

05 / Delivery plan

Build vertical slices in dependency order

Each phase should leave the app more truthful than before. Keep mocks only where they are clearly marked and do not expose future controls ahead of their behavior.

Phase 1

Foundation, navigation, and interface contracts

  • Replace the tab model with Explore, Applications, Inbox, and You.
  • Fix light and dark color tokens to meet WCAG AA for essential text and controls.
  • Set a 44 × 44 point minimum hit area and add visible keyboard focus.
  • Add semantic headings, navigation landmarks, labelled images, and selectable long-form text on web.
  • Create one accessible modal contract: dialog role, labelled title, focus containment, hidden background, Escape behavior on web, and focus restoration.
  • Expose pressed, checked, or selected state for chips based on their role.
  • Replace the custom PanResponder slider with accessible native and web controls.
  • Add typed English and Danish dictionaries, device-locale default, manual override, and Intl formatting.
  • Add explicit loading, empty, error, offline, denied, success, and destructive-confirmation patterns.
  • Constrain web content to a centered shell and hide unsupported native-only map behavior.
Exit condition All visible controls work or are removed. Core screens are keyboard reachable on web, understandable with screen readers, and usable at 200% text size.
Phase 2

Real Explore, detail, saves, and map

  • Connect the Expo client to Convex and replace mock listing reads.
  • Render the list with FlatList and stable keys.
  • Implement real filters, sort, result counts, save actions, and Browse or Saved segments.
  • Use the existing public/private listing boundary so exact address data never reaches public queries.
  • Add react-native-maps for iOS and Android. Keep web list-only for beta.
  • Store an exact private coordinate and a stable public coordinate displaced by about 250 meters.
  • Refresh after onRegionChangeComplete, debounced around 350 milliseconds.
  • Cap a map response at 100 pins. When exceeded, show a clear Zoom in to see homes message.
  • Start from manual city or area. Request location only after Near me and handle denial without a dead end.
Exit condition A user can browse, filter, save, open detail, and switch between list and a privacy-safe native map using real Convex data.
Phase 3

Profiles, applications, saved searches, and inbox

  • Generate and persist the device secret. Explain the lack of recovery or cross-device sync.
  • Trigger adaptive profile onboarding at the first application, not at first launch.
  • Request push permission during profile onboarding. Skipping cannot block an application.
  • Create an immutable application snapshot with an optional note and duplicate prevention.
  • Model pending, shortlisted, declined, withdrawn, and closed statuses.
  • Build Applications with clear status copy and the valid next action.
  • Create a conversation only after a server-authorized shortlist transition.
  • Build Inbox and message threads with offline, failed-send, report, and block states.
  • Persist saved searches and send Expo push notifications for matching newly published listings.
Exit condition A new user can move from a real listing to one submitted application, see its status, and enter a conversation only after shortlist.
Phase 4

Host dashboard, listing creation, and review

  • Turn the current listing prototype into a persistent draft with Basics, Details, Features, Location, Photos, and Review steps.
  • Branch fields for room, studio, apartment, and house without duplicating the whole form.
  • Geocode the private address and preview the approximate public location before publish.
  • Publish immediately after validation, then allow pause, edit, mark rented, and archive.
  • Add a host dashboard under You for listings, applications, and current status.
  • Keep the swipe deck with visible Pass and Shortlist controls, profile detail, and one-step undo.
  • Close outstanding applications when a listing is marked rented or archived.
Exit condition A device owner can publish and manage every supported rental type, then review and shortlist a real applicant without gesture-only controls.
Phase 5

Trust, deletion, release gate

  • Add report reasons: Scam, Inaccurate, Unavailable, Discriminatory, and Other.
  • Add blocking for conversations and prevent future contact between blocked device identities.
  • Apply default limits of 3 new listings per device per 24 hours, 5 active listings per device, and 10 reports per device per day.
  • Create an internal Convex moderation query and secret-protected takedown action. Do not build an admin app for beta.
  • Add Delete my data with clear scope, confirmation, progress, and cascade behavior.
  • Complete legal and privacy review for device identity, location handling, housing data, push notifications, retention, reporting, and deletion.
  • Run the full device QA matrix and distribute Expo development builds to the closed group.
Exit condition Abuse can be reported and stopped, user data can be deleted, legal and privacy questions are resolved, and both platform builds pass the beta acceptance checklist.

06 / Data and backend

Extend the existing Convex model, do not rebuild it

The backend already has useful foundations: device ownership, listings, saved listings, and private-address redaction. Keep those boundaries and add the smallest records needed to complete the product loop.

Record Key additions Required rule
ListingAdd studio, content language, exact private coordinate, displaced public coordinate, lifecycle, and moderation state.Only the owning device secret can mutate it. Public queries never expose exact address or coordinates.
ProfileUse a sharedHome or privateRental discriminant and fields relevant to that context.The device owner can update the current profile. Applications store a snapshot.
ApplicationListing, applicant device, snapshot, note, status, and transition timestamps.One active submission per device and listing. Only valid actors can transition state.
Conversation and messageApplication link, participants, messages, read state, block state.A conversation can exist only for a shortlisted application.
Saved searchFilters, area, notification preference, last match time.Match newly published listings and enqueue one bounded push notification.
Push tokenDevice identity, platform, token, permission state, last seen.Remove invalid tokens and do not treat denied permission as a product failure.
ReportReporter, target, reason, details, created time, moderation status.Rate-limit creation and keep the reporter private from the reported party.
Rate limitAction, hashed device identity, time bucket, count.Enforce on the server. Client messaging explains the next valid action.

Identity boundary

Generate a high-entropy secret on device, keep it in SecureStore, and hash it at the server boundary. Treat it as beta bearer authentication, not as a durable account.

Location boundary

Store exact location only for authorized host use. Derive one stable displaced public point so the pin does not move between sessions.

Metric boundary

Compute submissions, shortlists, and time-to-shortlist from first-party application timestamps. Add a full analytics system only after beta questions justify it.

Map implementation

Use the Expo-supported react-native-maps integration for SDK 55. The beta map is native only. Web should retain the list and filters inside a centered layout.

07 / Verification and release

Prove the whole loop on both platforms

Focused backend tests protect authorization and state transitions. Device QA protects the interaction contract. Both are needed because the highest-risk failures cross the client and server boundary.

Focused Convex tests

  • Device ownership and secret hashing
  • Private address and coordinate redaction
  • Listing lifecycle and publishing limits
  • Application uniqueness and allowed transitions
  • Shortlist gate for conversation creation
  • Saved-search matching and push enqueue behavior
  • Report and block authorization
  • Delete-my-data cascade and access removal

Manual iOS and Android QA

  • Light and dark themes, text at 200%, safe areas, keyboard, VoiceOver, TalkBack, and reduced motion
  • Browse, save, filter, sort, list, map, movement, and location denial
  • Every listing type and both adaptive profile types
  • Duplicate application, withdrawal, shortlist, and chat gate
  • Host create, publish, pause, edit, swipe, detail, undo, mark rented, and archive
  • Reporting, blocking, deletion, offline, slow, empty, and failed states

Beta acceptance checklist

  • bun run lint passes.
  • Focused Convex tests pass.
  • No essential text or control contrast failure remains.
  • No essential touch target is smaller than 44 × 44 points.
  • All dialogs have focus containment and restoration.
  • Every visible action has a real result and feedback.
  • Exact address and coordinates never appear in public responses.
  • The application-to-shortlisted-conversation flow completes on iOS and Android.
  • Push denial and location denial both have usable fallback paths.
  • Delete my data removes access and retained user-owned records as specified.
  • Web demo remains centered, keyboard usable, and list-only for maps.
  • Legal and privacy review is signed off before real users enter.
First implementation slice

Start with navigation, contrast, touch targets, modal behavior, i18n scaffolding, and removal of dead controls. Then wire one complete real-data path from Explore to room detail and save. This gives the product a truthful foundation before adding applications.
